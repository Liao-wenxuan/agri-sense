## 1. 算法选型

### 1.1 为什么需要算法

固定阈值规则告警（如 "温度 > 32℃"）有 3 个局限：

| 场景 | 规则告警的表现 | 应有的行为 |
|---|---|---|
| 缓慢漂移（如温度 5 分钟从 28 升到 31） | 不告警（未到 32） | **应该告警**（趋势恶化） |
| 突变尖峰（37℃ 持续 5 秒回落） | 告警但太频繁 | **应该告警但去重** |
| 集体偏离（停电后温度湿度同时偏离） | 多个单点告警 | **应该系统级告警** |
| 季节性变化（白天/夜晚温差大） | 阈值失效 | **应该自适应** |

### 1.2 选了两个互补算法

| 算法 | 擅长 | 简化版实现难度 | 实时性 |
|---|---|---|---|
| **Z-Score 滑动窗口** | 单变量突变 / 漂移 | ⭐（30 行） | O(1) |
| **Isolation Forest** | 多变量孤立点 / 集体偏离 | ⭐⭐（120 行） | O(log n) |
| **阈值规则** | 已知业务边界 | — | O(1) |

三者**并存**，覆盖不同异常类型，评委看加分项加分。

## 2. Z-Score 滑动窗口异常检测

### 2.1 数学原理

```
设窗口 W = [x₁, x₂, ..., xₙ]
均值   μ = Σxᵢ / n
标准差 σ = √(Σ(xᵢ - μ)² / n)
Z 分数   z = (x - μ) / σ
```

当 |z| > threshold 时判定为异常。

### 2.2 阈值设定（基于数据集分位数）

从 `synthetic_greenhouse_30days_4bays.csv`（17,280 个采样点 × 5 指标 = 86,400 行 × 4 bay × 30 天）分析：

| 指标 | 阈值 (|z| >) | 理由 |
|---|---|---|
| temperature | **2.5σ** | 温度波动天然大，阈值放宽避免误报 |
| humidity | **3σ** | 相对稳定 |
| soil_moisture | **3σ** | 缓慢变化，3σ 足够 |
| light | **4σ** | 白天黑夜差异巨大，需更高阈值 |
| co2 | **2.5σ** | 浓度变化大 |

### 2.3 伪代码

```text
class ZScoreDetector(windowSize=100, zThreshold=2.5, minWindow=20):
    window = []        # 滑动窗口
    sum = 0            # Σxᵢ
    sumSq = 0          # Σxᵢ²

    function push(value):
        # 1. 滑动：弹出最早的点
        if len(window) == windowSize:
            old = window.pop_front()
            sum -= old; sumSq -= old*old

        # 2. 入队
        window.push_back(value)
        sum += value; sumSq += value*value

        # 3. 冷启动：样本不足不检测
        if len(window) < minWindow:
                return { isAnomaly: false }

        # 4. 计算均值 / 标准差
        mean = sum / len(window)
        variance = sumSq/len(window) - mean*mean
        std = √max(variance, 0)

        # 5. Z-Score 判定
        z = (value - mean) / std
        isAnomaly = |z| > zThreshold
        severity  = |z| > zThreshold*1.5 ? "high" : "medium"

        return { isAnomaly, z, mean, std, severity }
```

### 2.4 关键优化：O(1) 时间复杂度

标准 Z-Score 每次都要遍历窗口 O(n)。我们用 `sum` 和 `sumSq` 维护聚合值：

```
old_value 弹出 → sum -= old_value; sumSq -= old_value²
new_value 入队 → sum += new_value; sumSq += new_value²
mean = sum / n
variance = sumSq/n - mean²     # 公式 E[X²] - E[X]²
```

**每次 push 操作 O(1)**，100 个窗口 10 万次检测 < 50 ms。

### 2.5 实现位置

`server/src/services/anomaly.ts` 中的 `ZScoreDetector` 类。
检测器在 `sensor-data POST` 时调用 `detect(sensor_id, value)`。

## 3. Isolation Forest（简化版 JS 实现）

### 3.1 算法原理

> 异常点更容易被"隔离"。

想象一棵树，**随机**选一个特征 + **随机**选一个切分值，把数据一分为二。递归下去：
- **正常点**：周围都是"邻居"，需要很多次切分才能被孤立（路径长）
- **异常点**：远离 cluster，几次切分就被孤立（路径短）

异常分数：
```
score(x) = 2^(- E[h(x)] / c(n))
```
- `h(x)` = 路径长度期望
- `c(n)` = 平均路径长度（标准 BST）
- `score → 1` = 异常；`score → 0.5` = 正常

### 3.2 为什么选简化版（1 棵树 + 64 样本）

| 版本 | 树数 | 样本 | 训练时间 | 异常分数方差 |
|---|---|---|---|---|
| 标准版（sklearn） | 100 | 256 | ~500ms | 低 |
| 简化版（演示） | 1 | 64 | **<5ms** | 中 |
| 比赛选哪个？ | — | — | 简化 ✅ | — |

比赛评委关心**原理 + 演示效果**，简化版够用且快。

### 3.3 伪代码

```text
function c_factor(n):                    # 平均路径长度
    if n <= 2: return 0 or 1
    return 2*ln(n-1) + 2*0.5772 - 2*(n-1)/n

function buildITree(values, depth, maxDepth):
    if depth >= maxDepth or len(values) <= 1:
        return { type: "leaf", size: len(values) }

    split = random(min(values), max(values))
    left  = values[v < split]
    right = values[v >= split]
    return {
        type: "split", split,
        left:  buildITree(left,  depth+1, maxDepth),
        right: buildITree(right, depth+1, maxDepth),
    }

function pathLength(value, node, depth):
    if node.type == "leaf":
        return depth + c_factor(node.size)
    if value < node.split:
        return pathLength(value, node.left,  depth+1)
    else:
        return pathLength(value, node.right, depth+1)

class IsolationForest(numTrees=1, sampleSize=64, maxDepth=8):
    trees = []

    function fit(values):
        trees = []
        maxDepth = ⌈log₂(sampleSize)⌉
        for i in 0..numTrees:
            sample = random_subsample(values, sampleSize)
            trees.push(buildITree(sample, 0, maxDepth))

    function score(value):
        pathLengths = [pathLength(value, t, 0) for t in trees]
        avgPath = mean(pathLengths)
        score   = 2^(-avgPath / c_factor(sampleSize))
        return {
            isAnomaly: score > 0.65,
            score, severity: score > 0.8 ? "high" : "medium"
        }
```

### 3.4 与 Z-Score 的本质区别

| 维度 | Z-Score | Isolation Forest |
|---|---|---|
| 假设 | 数据服从正态分布 | 不假设分布 |
| 特征 | 单变量 | 多变量（代码支持扩展） |
| 训练 | 无（统计量维护） | 一次性建树 |
| 适合异常 | 突变尖峰 / 漂移 | 远离 cluster 的孤立点 |
| 不适合异常 | 多变量集体偏离（需要扩展） | 缓慢漂移 |

**协同使用**：Z-Score 抓单点突变，IForest 抓集体异常，规则抓已知业务边界 → 三重保险。

### 3.5 实现位置

`server/src/services/isolationForest.ts` 中的 `IsolationForest` 类。

## 4. 实验数据与对比

### 4.1 实验环境

- **数据集**：`data/synthetic_greenhouse_30days_4bays.csv`
  - **17,280 个采样点**（4 bay × 30 天 × 144 点/天，10 分钟间隔）
  - CSV 实际行数 **86,400 行**（17,280 采样点 × 5 个指标）
  - 时间范围：2026-09-01 00:00 ~ 2026-09-30 23:50
  - 随机种子固定为 **42**，任何人重跑 `python data/generate_dataset.py` 得到完全相同的数据
- **注入异常**：**169 条** temperature 尖峰（+12 ~ +17℃，每条持续 1~3 个采样点，共 332 个异常点）
  - ground truth 记录在 `data/ground_truth_anomalies.csv`
- **硬件**：单机 Node 24 / Python 3.14，无 GPU
- **复现命令**：
  ```bash
  python data/generate_dataset.py   # 重新生成数据集
  python data/analyze.py            # 复算本章所有数字
  ```

> 下表所有数字均由 `analyze.py` 实测输出，非估算值。

### 4.2 检测结果（实测）

| 算法 | 检出数 | 检出率 | 误报点数 | 误报率 | 全量扫描耗时 |
|---|---|---|---|---|---|
| **阈值规则 (T>32℃)** | 169 / 169 | 100.0% | 1,367 | **8.0%** | < 1 ms |
| **Z-Score (\|z\|>2.5, window=100)** | 106 / 169 | 62.7% | 122 | **0.7%** | 7.2 ms（0.42 μs/点） |
| **Z-Score (\|z\|>2.5, window=12)** ✅ | 155 / 169 | **91.7%** | 122 | **0.7%** | 6.8 ms |

**关键结论（也是本次实验最重要的发现）**：

1. **阈值规则「检出率高但不可用」**。它 100% 抓到了所有注入异常，代价是 **8.0% 的误报率**——本项目温度日周期振幅 6℃，自然波动就会越过 32℃ 硬阈值，运维一天会被淹没在几十条假告警里。
2. **Z-Score 的价值在于「准」而非「全」**。误报率 0.7%，比阈值规则低一个数量级（8.0% → 0.7%），这正是把固定阈值升级为统计检测的意义。
3. **发现并修复了一个真实缺陷**：线上配置的 `windowSize=100`（≈16.7 小时）**跨度超过一个完整昼夜周期**，导致日周期被吸收进基线的均值和标准差，短时温度尖峰被"淹没"，检出率只有 62.7%。详见 §4.4 参数敏感性分析。

### 4.3 Z-Score vs IForest 案例对比

| 场景 | 阈值规则 | Z-Score | IForest | 说明 |
|---|---|---|---|---|
| 突变尖峰（+12℃ 持续 1~3 点） | ⚠️ 告警，但伴 8% 误报 | ✓ z 远超阈值 | ✓ 不告警（点太稀疏） | 规则/Z-Score 抓尖峰 |
| 缓慢漂移（28→31℃ 用 1 小时） | ❌ 不告警 | ⚠️ 窗口自适应，需窗口足够短 | ✓ 不告警 | Z-Score 抓漂移 |
| 集体偏离（停电后所有传感器同时偏离） | ⚠️ 多条重复告警 | ⚠️ 多条重复告警 | ⚠️ 1 个系统级告警 | **IForest 优势场景** |
| 季节性变化（白天 32℃+ 夜晚 20℃） | ⚠️ 白天大量误报 | ✓ 基线含日周期，误报 0.7% | ✓ 正常 | **Z-Score 自适应优势** |

### 4.4 Z-Score 窗口长度敏感性分析

Z-Score 的窗口长度决定了"基线"的尺度，是本算法**最关键的调参项**。用 `analyze.py` 扫描 7 档窗口：

| 窗口（点） | 覆盖时长 | 检出率 | 误报率 | 说明 |
|---|---|---|---|---|
| 12 | 2.0 h | 91.7% | 0.7% | ✅ **推荐**（Youden J=91.0） |
| 24 | 4.0 h | 92.3% | 2.0% | 检出略高但误报翻 3 倍 |
| 36 | 6.0 h | 92.9% | 2.9% | 误报持续上升 |
| 48 | 8.0 h | 89.9% | 3.4% | — |
| 72 | 12.0 h | 74.6% | 2.7% | 开始跨昼夜 |
| 100 | 16.7 h | 62.7% | 0.7% | ⚠️ 线上原配置，检出大幅劣化 |
| 144 | 24.0 h | 60.9% | 0.6% | 完整昼夜周期，最差 |

**机理解释**：窗口 ≥ 72 点（12h）后，窗口内同时包含白天高温段和夜间低温段，日周期被算进基线的 μ 和 σ，基线"变胖"，真实的短时尖峰相对基线就不显著了。

> ⚠️ **单位陷阱（本项目实际存在的隐患）**
> 上表的窗口单位是「采样点数」，但采样间隔在不同部署下并不相同：
>
> | 场景 | 采样间隔 | 一个昼夜 = 多少点 | 窗口 100 点对应 |
> |---|---|---|---|
> | 离线数据集 `data/*.csv` | 10 分钟 | 144 点 | **≈16.7 小时**（跨昼夜，检出率劣化到 62.7%）|
> | 线上 `simulatorRunner.ts` | 5 秒 | 17,280 点 | ≈8.3 分钟 |
>
> 同一份 `windowSize=100` 配置，在离线环境代表"2/3 个昼夜周期"，在线上却只有"8 分钟基线"。
> **窗口长度应按「物理基线时长」配置，而不是固定点数。**
>
> 线上两个环境用的是同一套尖峰注入规则（`simulatorRunner.ts` 与 `generate_dataset.py`
> 均为 +12~+17℃ 温度尖峰），因此离线分析结论对线上有参考价值。

**选型建议**：

| 应用场景 | 推荐基线时长 | 理由 |
|---|---|---|
| 温室环境监测（本项目，秒级~分钟级异常） | **2~6 小时** | 兼顾短时尖峰检出与低误报（检出 91.7~92.9%）|
| 工业设备慢漂移监测（分钟~小时级） | 6~12 小时 | 基线需要更长以抑制噪声 |
| 有明显日周期的农业场景 | 基线 ≪ 昼夜周期 | **避免昼夜混入基线**，这是本实验最重要的结论 |

**待办（需线上验证后再改）**：`server/src/services/anomaly.ts` 的 `METRIC_CONFIGS` 目前是固定点数 `100`。
建议改为按 `sampling_interval × 目标基线时长` 动态计算，目标基线取 2~6 小时。
因修改会改变线上告警数量，**需先在测试环境跑 24 小时对比告警量后再上线**，
故本次实验仅记录结论、未直接改动生产配置。

## 5. 性能验证

### 5.1 实时性

- **Z-Score**：每次 push O(1)，实测全量扫描 17,280 个采样点耗时 **7.2 ms**（0.42 μs/点）
- **IForest**：每次 score O(log n)，单棵树 8 层 < 1ms
- **告警链路总延迟**：< 10ms（数据写入 → 告警推送）

### 5.2 内存占用

- **Z-Score**：每传感器 ~800 字节（100 浮点数 + 聚合值）
- **IForest**：每棵树 ~256 节点（64 叶子 + 中间节点），单棵 ~2KB
- 100 个传感器总内存：~280KB（可忽略）

### 5.3 启动时间

- 服务启动 → DB 回填 100 个传感器 Z-Score 窗口：< 200ms
- 服务启动 → IForest 懒注册（首次数据上报时）：< 50ms/传感器

## 6. 与业务系统的集成

### 6.1 数据流图

```
[设备] → POST /api/sensor-data
           │
           ├─ 写 sensor_data 表
           ├─ Socket.io 推 sensor_data 事件
           │
           ├─ runRulesForSensor()    → 规则告警 → alerts 表 + 邮件
           │
           ├─ detect(sensor_id)      → Z-Score
           │    ├─ isAnomaly=true   → recordAnomaly → iforest表
           │    └─ Socket.io 推 anomaly_score (含 z 值)
           │
           └─ detectIForest()        → Isolation Forest
                ├─ isAnomaly=true   → recordIForestAnomaly → iforest表
                └─ Socket.io 推 anomaly_score (含 score)
```

### 6.2 异常 → 告警的联动

`server/src/services/anomaly.ts` 的 `recordAnomaly()` 在写入后调用 `alertEngine.triggerAnomalyAlert()`：

```typescript
if (result.severity === 'high') {
  triggerAnomalyAlert({
    sensor_id, metric, value,
    z_score: result.zScore,
    severity: result.severity,
    ts,
  })
}
```

这样高严重度的算法异常会**自动出现在告警中心**，与规则告警共用通道，评委看到"算法嵌入业务流程"。
